# カスタムボタン — 改訂設計書

- 文書ID: **CPP-DESIGN-15**
- 状態: **実装済み（2026-10-22）**
- 改訂日: 2026-10-22
- 依存: `00-architecture.md`、`03-prompt-actions.md`、`04-tabs-layout.md`、`05-settings-storage.md`、`06-options-page.md`、`07-clipboard.md`、`09-testing.md`
- 目的: 既定20ボタンに加え、既存4操作のいずれかを使うボタンをユーザーが追加・編集・表示切替・並べ替え・削除できるようにする。
- この改訂では、現行の `settings.ts`、`default-ui.ts`、`settings-repository.ts`、`options-state.ts`、`OptionsPage.tsx`、`Panel.tsx` の実装構造を踏まえ、保存競合、削除、操作実行、リセット、JSON入出力の境界を具体化する。

## 1. 対象と不変条件

### 1.1 初版の対象

- Optionsの既存6グループ（`always` と既存5タブ）に、カスタムボタンを作成する。
- 各ボタンは既存4操作のうち **1操作だけ** を実行する。
- ラベル、色、表示状態、定型文の場合は本文を編集する。グループ内の並び順を既定ボタンと混在して変更できる。
- カスタムボタンの追加・変更・削除はOptionsのドラフトに反映し、**保存成功後にのみ** Content Scriptへ反映する。
- 設定のJSON入出力、他のChatGPTタブへの設定変更通知、既定値復元に対応する。

### 1.2 対象外

- 新しいタブ・グループの作成、作成後のグループ間移動。
- 複数操作の連続実行、任意スクリプト・JavaScript、未定義の操作種別。
- ChatGPTへの自動送信、非公開API、CodexBridgeへの通信。
- 既定20ボタンの削除、既定ボタンの内部ID・操作種別の変更。

### 1.3 絶対に維持する条件

1. 既定20ボタン・既定5タブ・既存ユーザー設定を変更せずに読み込めること。
2. 既定ボタンは従来のID、既定文面、操作契約を維持すること。
3. カスタムボタンは未送信の文章・選択範囲を既存操作以上に破壊せず、**送信処理を行わない** こと。
4. 無効な設定、競合、保存失敗で既存の保存済み設定を上書きしないこと。
5. 「既定値に戻す」はカスタムボタンを削除しないこと。削除は明示的な操作（または削除を明示したJSON置換）のみとすること。
6. 会話統計の `chatPanelPlus.statistics`、パネル状態の `chatPanelPlus.viewState`、回答完了音設定など、無関係な保存データを損なわないこと。

## 2. 操作契約

既存の `03-prompt-actions.md`、`07-clipboard.md` と実際の既定ボタンの処理を再利用する。カスタムボタン独自の入力欄操作方式は実装しない。

| 操作種別 | `kind` / `action` | 編集可能項目 | 実行結果 |
| --- | --- | --- | --- |
| 定型文挿入 | `kind: 'insert'`（`action`なし） | ラベル・色・本文 | Composerの先頭に本文を差分挿入 |
| 現在時刻 | `kind: 'action'`, `action: 'insert-jst'` | ラベル・色 | 既存形式のJST日時をComposer先頭へ挿入 |
| クリップボード | `kind: 'action'`, `action: 'paste'` | ラベル・色 | 既存の選択範囲保存・貼付・フォールバックを使用 |
| クリア | `kind: 'action'`, `action: 'clear'` | ラベル・色 | 既存のクリア処理を使用 |

- `insert`では`text: string`を必須とし、空文字も有効な本文として扱う。
- `action`では`text`を持たせない。`insert`では`action`を持たせない。
- 操作種別は作成後もOptionsで変更できる。切替時は`kind`/`action`/`text`を**一括で適正な組み合わせへ置換**し、不要フィールドを残さない。`action`→`insert`では本文を空文字から編集可能とし、`insert`→`action`では旧本文を定義から除去する。ボタンIDとグループは維持する。
- 既存のエラー通知、Composer切替検知、クリップボード許可失敗時の対応を流用する。

## 3. 設定モデルとID

### 3.1 保存先

保存先は従来どおり **`chatPanelPlus.config`**。`schemaVersion: 1`の任意フィールド`customButtons`を使用し、既存の正当なv1設定はそのまま読み込めるようにする。新しいChrome権限や独立Storageキーを増やさない。

概念型（既存の型・命名規約に合わせて実装時に調整可）:

```ts
type CustomButtonId = `custom-${string}`;

type CustomButtonDefinition =
  | {
      readonly groupId: ButtonGroupId;
      readonly label: string;
      readonly color: string;
      readonly visible: boolean;
      readonly kind: 'insert';
      readonly text: string;
    }
  | {
      readonly groupId: ButtonGroupId;
      readonly label: string;
      readonly color: string;
      readonly visible: boolean;
      readonly kind: 'action';
      readonly action: 'insert-jst' | 'paste' | 'clear';
    };

type CustomButtons = Readonly<Record<CustomButtonId, CustomButtonDefinition>>;
```

`ExtensionSettings`に`customButtons?: CustomButtons`を追加する。`buttonOrder[groupId]`には既定IDと、当該グループに属するカスタムIDを混在させる。

### 3.2 IDの生成と検証

- 作成時にブラウザの暗号学的乱数に基づく `custom-${crypto.randomUUID()}` を生成する。ラベル、グループ名、順序からIDを作らない。
- IDは保存・JSON出力・再読込後も変更しない。既定IDとは別の名前空間に置く。
- 読み込み・インポートでは`custom-`接頭辞と所定のUUID形式を検証し、既定IDとの衝突や重複を拒否する。
- JSONオブジェクトに同一キーが複数書かれた場合は通常の`JSON.parse`で重複が失われるため、**重複キーの存在自体の検出を保証しない**。少なくとも解析後の実体についてID整合性とグループ所属を厳格に検査する。
- IDを再利用して「削除した別ボタン」を復活させない。削除後の作成では新しいIDを採番する。

### 3.3 バリデーション

- `customButtons`がない場合は空集合として扱う。空の `{}` も有効とする。
- `customButtons`と各定義は通常のオブジェクトでなければならない。
- `groupId`は`always`または既存5タブのみ。`kind`/`action`/`text`は第2節の判別可能な組み合わせのみ。
- `visible`はboolean、`label`/`text`はstring、`color`は既存のHEX色検証規則に従う。
- カスタム定義の未知の実行フィールド、追加の`action`や`text`など、操作を曖昧にする値は拒否する。ユーザー文字列をHTML・コードとして実行しない。
- 既存設定スキーマの未知の**無関係な**フィールドに関する後方互換性の方針は維持する。ただし`customButtons`は既知フィールドになるため必ず検証し、無検証のままパネルに渡さない。
- 不正なカスタム定義を検出した場合は、読み込み時に黙って削除・再保存しない。設定全体の保存を止め、理由を報告して原本を保護する。インポートでは適用を拒否する。

## 4. ボタン順序の解決

1. グループごとに、既定ボタンと当該グループに属する有効なカスタムボタンを候補として確定する。
2. `buttonOrder[groupId]`を読み、既知IDを順序どおりに一度だけ採用する。
3. 順序配列にない既定IDを既定順で末尾に補完し、順序配列にないカスタムIDを安定した決定的順序で末尾に補完する。
4. 異なるグループのカスタムIDを参照する順序配列は不正として拒否する。削除されたカスタムIDへの参照は、**削除を行う同じドラフト操作内で**必ず除去する。
5. カスタム作成時は対応グループの末尾へIDを追加する。グループが非表示でも定義と順序は保持する。
6. 非表示ボタンも順序計算には残し、表示時だけ除外する。再表示時には元の位置へ戻る。

既存の`orderedIds`は既定IDしか解決しないため、`settings.ts`と`default-ui.ts`双方の順序解決・正規化を拡張する。**片方だけの変更でカスタムIDが消えないこと**をテストする。

未定義の`custom-`IDや所属の異なるIDを含む外部JSONは拒否する。一方、従来スキーマで許容していた通常の未知IDの取り扱いは、不必要に互換性を狭めないよう既存契約を踏襲する。

## 5. Optionsでの操作

### 5.1 新規作成

- 常時表示および各タブの設定グループに「ボタンを追加」を置く。
- 作成フォームで操作種別、ラベル、色、必要なら本文を指定する。
- 初期状態は`visible: true`、選択したグループの末尾。初期ラベル・色は既存操作に対応する妥当な既定値を使う。
- 新規ID生成とドラフト追加は一度の操作として行い、保存前のドラフト内でもIDを安定させる。ReactのレンダリングごとにIDを生成しない。
- フォームの取り消しや保存前の再読み込みでは、保存していないボタンを永続化しない。

### 5.2 編集・削除・並べ替え

- 既定ボタンの編集機能を維持し、カスタムには「操作種別」「表示」「ラベル」「色」「本文（`insert`のみ）」「上下移動・ドラッグ」「削除」を提供する。
- 削除はカスタムボタンにだけ提供する。削除操作では`customButtons[id]`と`buttonOrder`内の同IDをドラフトから同時に除去する。
- 削除は保存前に取り消せる。保存後の削除を復元するにはJSONバックアップ等が必要であることを確認UIで示す。
- プレビューはドラフト状態を表示し、パネル本体は保存成功後に更新する。
- キーボードで順序を変更でき、ドラッグだけを必須にしない。色だけに依存せずラベルとボタンIDを確認できる。

### 5.3 実行ディスパッチャー

現行`Panel.tsx`の常時表示群では`paste`だけが`beginPaste()`を経由し、タブ内は`activate()`経由となっている。現在の`activate()`は`paste`を扱わないため、**タブ内に追加したカスタム貼付ボタンをそのまま描画しても正常に実行できない**。

実装では、既定・カスタム、常時表示・タブ内の区別なく、**同一のアクションディスパッチャー**へ集約する。

- `paste`は配置場所にかかわらず既存の選択範囲取得（必要な`pointerdown`処理）→クリップボード処理→失敗時フォールバックを通す。
- キーボードクリック時にも既存の選択範囲取得・安全なフォールバックを用いる。
- `insert`・`insert-jst`・`clear`も既存処理を共有する。ラベル文言から操作を推測しない。
- 1操作につき1回だけ実行し、自動送信、Enter合成、無関係なComposer変更を行わない。

## 6. Repositoryでの追加・更新・削除・競合

### 6.1 保存の基本方針

- `saveSettings(base, draft, ...)`は従来どおり **最新の保存値を読み、変更箇所だけを統合** する。
- `customButtons`全体を1つの通常差分として置換せず、**ボタンID単位**で作成・更新・削除を識別する。1つのIDを単位として競合を検出すればよい。個々のラベル・色までフィールド単位に分割することは初版必須ではない。
- `base`と`draft`のカスタムID集合の和から、追加（未存在→存在）、更新（内容変更）、削除（存在→未存在）を生成する。削除は、最新値にも存在することと、その内容が期待値から変わっていないことを確認する。
- `latest`側で同じIDが変更・削除された場合、競合を返してドラフトを保持する。新規追加した別IDがある場合は、最新値の別IDを保持する。
- `buttonOrder[groupId]`は従来と同じくグループ単位の競合対象とし、最終的に`customButtons`と整合する順序配列を保存する。追加・削除に伴う配列更新を取りこぼさない。
- 保存後、Repositoryが返す確定値をOptionsの`base`/`draft`に反映する。

### 6.2 同時編集の限界

- 現行の設定保存はWeb Locksが利用できる呼び出しでは直列化されるが、Chrome Storageには比較交換（CAS）がない。Web Locksを共有しない書き手との厳密な原子性は保証できない。
- 同じグループの`buttonOrder`を別のOptionsウィンドウが同時に編集した場合は、**勝手に順序を混ぜず競合として保存を拒否**して再読み込みを促す。
- 異なるボタンIDの並行変更は、同じ順序配列を変更しない限り可能な範囲で統合する。
- ID生成がUUIDでも、「別ウィンドウによる作成」「削除済みIDへの参照」「古いドラフトによる復元」を含め、追加・更新・削除それぞれの競合テストを行う。
- 競合・読み込み失敗・容量超過・バリデーション失敗では保存済み値を保護し、成功通知やパネル反映を行わない。

## 7. 既定値復元とJSON入出力

### 7.1 「既定値に戻す」

- リセット対象は既定20ボタンの上書き設定・既定の並び、既定5タブの表示・並び、選択タブと最小化状態とする。回答完了音など無関係な設定の扱いは既存のリセット契約に従い、勝手に変更しない。
- **`customButtons`の定義・ラベル・色・本文・表示状態・IDは全件維持**する。
- 各グループの`buttonOrder`を「そのグループの既定ボタンの既定順 + 既存カスタムIDの相対順」に再構成する。カスタムIDのグループ所属は変えない。
- 現行のOptionsが行う`setDraft(DEFAULT_SETTINGS)`を、そのままカスタム導入後のリセット操作に流用しない。カスタムを維持するドラフト変換を実装する。
- 古いOptionsドラフトを基にリセットすると他ウィンドウの最新カスタム追加を消すおそれがある場合は、最新値との整合を確認し、必要なら競合として保存を止める。

### 7.2 JSONエクスポート

- 設定本体だけを書き出し、`customButtons`と`buttonOrder`を含める。会話本文、クリップボード、会話統計、`viewState`は含めない。
- `customButtons`が空の設定も書き出せる。v1の旧設定を読み込める互換性を保つ。
- JSONのボタンID、本文、改行、色、順序は往復で維持する。

### 7.3 JSONインポート

- ファイルを解析・検証し、**保存中のカスタムボタン数／インポート後の数／削除予定のID**を適用前プレビューに示す。
- `customButtons`が明示されているJSONでは、その集合を意図するものとして扱う。現在の保存済み集合から消えるカスタムIDがあれば、適用前に削除を明示して確認する。明示的な空オブジェクト`{}`は「全カスタム削除」を表し得るため、特に確認する。
- `customButtons`を持たない旧v1 JSONは、カスタム機能登場前の形式とみなし、**既存のカスタム定義を保持**してインポートする。既定ボタン・タブ設定については従来の置換仕様を使う。
- 旧JSONの順序配列にカスタムIDがない場合は、既存カスタムIDを当該グループの末尾へ決定的に補完する。
- インポートしたカスタム集合を適用する処理でも、`base`から`latest`までの変更を確認し、後から別ウィンドウで追加・更新されたIDを黙って削除しない。必要な場合は競合エラーを返して再読込を促す。
- JSON検証エラー、削除確認の取り消し、競合、保存失敗では元の保存値と編集ドラフトを保護する。

## 9. 自動テスト受入条件

### 9.1 型・保存・読み込み

- 旧schemaVersion 1設定（`customButtons`欠落）が従来どおり解決される。
- 4操作の正しい定義、本文空文字、複数グループ、非表示ボタン、作成後の操作種別変更を保存・再読込できる。切替後に古い`action`や`text`が残らない。
- UUID形式・既定ID衝突・不明グループ・異なるグループへの順序参照・未知action・kind/action/text不一致・不正色・不正型を拒否する。
- 順序配列からの補完、重複の排除、削除時の順序参照除去が正しい。
- カスタムの追加・更新・削除と、既存設定フィールドの変更を混同しない。

### 9.2 競合・保全

- 別IDの変更を可能な範囲で統合し、同一IDの競合追加・更新・削除では黙って上書きしない。
- 同一グループの順序競合はエラーとしてドラフトを保護する。
- 変更通知後、現在開いている複数タブに同じ確定設定が反映される。
- 保存失敗、破損データ、旧ドラフトによる更新でも、既存カスタムボタン・他設定・会話統計を失わない。

### 9.3 UI・操作

- 既定・カスタム双方で挿入、時刻、クリア、貼付が正しい既存操作を利用する。
- **タブ内カスタム`paste`**をマウス・キーボードで実行し、選択範囲・Composer切替・権限拒否時フォールバックを維持する。
- 操作を自動送信しない。操作種別をラベル文字列から推測しない。
- 追加・操作種別変更・削除の保存前取り消し、保存後反映、非表示・再表示、上下移動・ドラッグが正しい。
- 「既定値に戻す」はすべてのカスタム定義を保持し、グループの末尾に配置する。
- 旧JSONではカスタムを保持し、`customButtons`を明記したJSONの削除予定を確認できる。エクスポート→復元→インポートの往復でID・本文・順序を維持する。

### 9.4 検証コマンドと実機確認

実装・自動テスト後に以下を実施する。

```powershell
pnpm typecheck
pnpm lint
pnpm test
pnpm build
pnpm check:size
```

Chrome実機での確認事項は別途記録する。少なくとも、Optionsでの4操作追加、保存成功後のパネル反映、タブ内貼付、削除取り消し、リセット後の保持、JSON往復、F5・SPA遷移・複数タブ設定通知を確認する。

## 10. 実装状況（2026-10-22）
