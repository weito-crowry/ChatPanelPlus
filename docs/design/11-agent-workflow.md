# Codex Luna 実装オーケストレーション・レビュー規約

- 文書ID: CPP-DESIGN-11
- 状態: 初版（運用方針。これ自体は実装・委任・commit を許可しない）
- 依存: 00～10 の設計書、AGENTS.md
- 想定: ChatGPT が設計と独立レビューを担当、Codex Luna が実装管理・自己レビューを担当し、必要なら Luna サブエージェントを小タスクに割り当てる。

## 1. 基本方針

- ChatGPT: 設計責任者。仕様・インターフェース・受入条件・設計変更の判断・最終独立レビューを担当する。
- Codex Luna オーケストレーター: 承認済み設計を読んでタスクを分解し、依存関係・進捗・テスト・統合・自己レビューを管理する。
- Luna 実装担当（サブエージェントを利用可能な場合）: 1タスクずつ必要最小限のコード、テスト、ドキュメントを実装し、結果と残件を報告する。
- AGENTS.md は原則としてサブエージェント・別モデルへの委譲・新規 worktree を使用しない。今回の設計文書作成では使用しない。将来の実装で委譲を許可する場合は、ユーザーの明示承認と実行環境の対応を確認する。
- サブエージェントの利用可否に関わらず、単一 Luna による逐次実装で同じ品質ゲートを適用できるようにする。
- モデル名は実装環境の利用可能性に応じて確認し、指定モデルの使用を検証せず断定しない。

## 2. 作業開始プロトコル

オーケストレーターは毎回次を行う。

1. AGENTS.md、当該フェーズの設計書、現在のソース、Git状態、未追跡ファイルを読む。
2. ユーザーが許可した実装範囲、作業対象の checkout、書込可能ファイル、禁止事項を確認する。
3. 依存する実装が完了しているかを確認。未完成であれば先行タスクへ戻す。
4. 変更ファイル一覧、公開インターフェース、受入基準、テスト計画を小タスク単位で定義する。
5. サブエージェント使用が承認されている場合だけ、限定スコープの実装を1つずつ委任する。必要性がなければ単独で実装する。
6. コード変更を開始する前に未追跡ファイルが消えないことを確認する。新 worktree を無断で追加しない。

## 3. 1タスクの成果物

- 対応する設計文書 ID とセクションへの参照
- 変更したファイル一覧と実装した機能
- コード変更・追加テスト・既存テスト回帰の結果
- 公開 API・型・設定スキーマ変更の内容
- Chrome 実機で確認が必要な操作と未検証事項
- 技術的な逸脱・設計で定義されていない判断が必要な点

機能を完成させるために仕様を変更する必要が生じたら、実装者だけで設計を上書きしない。理由と影響範囲を提示して設計責任者の判断を待つ。

## 4. 実装者セルフチェック

- 元 v7.2 のボタン内容、タブ、初期配置・色・外観を改変していない。
- 自動送信や ChatGPT API 呼び出しが新たに加わっていない。
- Range、カーソル、未送信本文、クリップボードの失敗時処理が設計通り。
- 新しい storage 権限や Chrome 権限は必要性が確認されている。
- 境界外の既存ファイルを編集していない。コードサイズと新規依存は適正。
- 単体・統合テストを追加し、各種検査に合格した根拠を添付する。
- 実機未検証項目をテスト済みと報告していない。

## 5. Luna オーケストレーターのレビュー

実装担当と同じモデルを使う自己レビューには、同じ誤解を繰り返すリスクがある。主観的な「問題なさそう」ではなく、次の証拠に基づいてレビューする。

- 指定したファイル以外が変更されていないか、既存未追跡資産を保護したか。
- 仕様の各受入条件に対応するテストがあるか。
- テストの結果が実測であり、ログや PASS 件数が具体的か。
- 新機能以外の ChatGPT 表示・会話読み込み・既存 OPEN_OPTIONS に回帰がないか。
- タイムアウトや API 拒否時に空振りを成功と見なしていないか。
- レビューフィードバックを受けて修正し、再試験したか。

不合格のタスクを次のフェーズへ進めない。特にユーザーの未送信本文消去、誤送信、誤 Composer 編集は重大欠陥として停止。

## 6. 実行権限の境界

- 通常のソース編集、テスト、ビルドはユーザーが当該実装フェーズを承認した範囲だけ行う。
- git add/commit/push/PR/merge、別ブランチ・worktree 作成、Chromeロード元デプロイ、拡張再登録などは別途明示承認を得る。
- リポジトリが unborn branch であることを常に踏まえ、git diff を唯一の変更根拠にしない。
- 既存ファイルの削除、無断 reset/clean/stash、無関係な依存更新をしない。
- ローカル Windows 環境以外でのビルド・試験を勝手に導入しない。
- Chrome の新IDフォルダへの通常の直接編集・手動コピー・移動・改名・削除・再登録をしない。ユーザーが明示的に承認した場合に限り、検証とバックアップを経由する pnpm deploy:chrome による成果物更新を許可する。承認なしの deploy は禁止する。Chrome 拡張の再読み込みはユーザーが別途手動で行う。

## 7. チェックポイントと最終受入

- まずデフォルト定義、次に入力欄アダプター、React UI、タブ・最小化、クリップボード、設定・Options、DOM復旧、統合の順に管理する。
- 各フェーズ完了でテスト結果・未検証事項・次フェーズの依存を記録し、重大な仕様不整合だけを ChatGPT へ差し戻す。
- 全機能完了後、ChatGPT は設計書、実装差分、テストログ、実機結果を基に独立レビューを行う。
- 最終レビューで指摘された問題は同じ品質ゲートを通して再修正する。
- Chrome 上の実機確認が未完なら、テスト合格を以て完成・品質保証と断定しない。

## 8. 完了報告フォーマット

- 目的・対象フェーズ・設計書ID
- 開始時 Git 状態と終了時 Git 状態
- 実装内容と変更ファイル
- 検証コマンドと実測結果（PASS/FAIL/未実施）
- Chrome実機確認（確認者、確認した操作、未確認操作）
- 重大問題・残リスク・設計からの逸脱
- コミット・Push・デプロイの実施有無
- 次に行う最小タスク

報告だけで勝手に作業範囲を広げない。
